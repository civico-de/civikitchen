# Configuration

The images read their settings from environment variables. Variables starting with `CIVIKITCHEN_` control CiviKitchen's own behaviour. The `CIVICRM_` prefix is reserved for three things: the contract with CiviCRM itself (`CIVICRM_AUTO_INSTALL` and the `CIVICRM_DB_*` variables, from which core builds its DSN at boot), the description of the CiviCRM or civibuild target (`CIVICRM_VERSION`, `CIVICRM_SITE_TYPE`), and CiviCRM's own variables such as `CIVICRM_UF`.

Older kitchen variables spelled with `CIVICRM_`, and `SITE_URL`, still work but print a deprecation warning. The Image column marks variables that only make sense for one image family.

| Env var | Default | Image | Purpose |
|---------|---------|-------|---------|
| `CIVICRM_DB_HOST` | `db` | all | Database host name. |
| `CIVICRM_DB_PORT` | `3306` | all | Database port. |
| `CIVIKITCHEN_SITE_URL` | derived | all | The URL the browser opens. CiviCRM bakes it into asset paths, so it must match the host and port you use, or assets return 404. On the demo images it rewrites the baked base URL at boot ([Demo images](images.md#demo-images)). |
| `CIVICRM_AUTO_INSTALL` | `0` | standalone | Set to `1` to install CiviCRM on first start, when `civicrm.settings.php` is missing. |
| `CIVICRM_DB_NAME` | `civicrm` | standalone | Database name. The standalone image connects as the app user. Buildkit creates the database and user itself. |
| `CIVICRM_DB_USER` | `civicrm` | standalone | Database user of the running CiviCRM. |
| `CIVICRM_DB_PASSWORD` | `civicrm` | standalone | Password for `CIVICRM_DB_USER`. |
| `CIVIKITCHEN_DEMO_USER` | _(unset)_ | standalone | Creates a CiviCRM login with this username and the admin role during auto-install. Requires `CIVICRM_AUTO_INSTALL=1`. |
| `CIVIKITCHEN_DEMO_PASS` | `admin` | standalone | Password for the demo user. |
| `CIVIKITCHEN_DEMO_EMAIL` | `admin@example.org` | standalone | Email address on the demo user's contact record. |
| `CIVIKITCHEN_COMPONENTS` | all standard | standalone | Comma-separated components to enable at install. The default is the full set: CiviEvent, CiviContribute, CiviMember, CiviMail, CiviPledge, CiviCase, CiviReport and CiviCampaign. Narrow the list, or pass an empty string to get cv's core-only default. |
| `CIVIKITCHEN_SMTP_HOST` | _(unset)_ | all | Points CiviCRM's mailing backend at this SMTP host after install. The example compose stack uses maildev, so outbound mail shows up in its UI on port 1080. On the buildkit flavors it also removes buildkit's `app/civicrm.settings.d/100-mail.php`. That file cannot see the database-level backend and would set `CIVICRM_MAIL_LOG=/dev/null`, which silently swallows all outbound mail. |
| `CIVIKITCHEN_SMTP_PORT` | `1025` | all | Port for `CIVIKITCHEN_SMTP_HOST`. |
| `CIVIKITCHEN_EXTRA_EXTENSIONS` | _(unset)_ | all | Comma-separated extension keys to download and enable after install, for example `de.systopia.xcm,de.systopia.twingle`. Runs once during first-boot provisioning. A bare key comes from its verified source if a mounted extension's `civikitchen.yaml` declares a version-constrained, digest-pinned entry for it under `policy.extension_sources`. An explicit `key@URL` value is an operator override and does not count as pinned. The requirements an entry declares and the site lacks take such a pin the same way, else come from the registry, and are installed and enabled before the entry. |
| `CIVIKITCHEN_ENABLE_EXTENSIONS` | _(unset)_ | all | Sets the enable order. Every extension bind-mounted into `/var/www/html/ext` is enabled after install without being listed here. Each extension's `<requires>` in `info.xml` is resolved first. A missing dependency comes from the registry, or from its `policy.extension_sources` entry (Composer version constraint, HTTPS and SHA-256), and is enabled before the extension. CiviCRM downloads an extension only once its own requirements are installed, so these are installed and enabled before the download. |
| `CK_DEP_ARCHIVE_DIR` | _(unset)_ | all | Directory of dependency release archives staged from outside the container. It is read when a `policy.extension_sources` entry pins a dependency to a `release:` instead of a `url:`. The entrypoint checks each archive against its pinned SHA-256. A release pin without its archive here is an error and never falls back to the registry. The web user (`www-data`, `buildkit` on the buildkit images) reads the archives, so they have to be readable for it. See [A dependency only a credential can reach](extension-releases.md#a-dependency-only-a-credential-can-reach). |
| `CIVIKITCHEN_LOCALES` | _(unset)_ | all | Comma-separated locales, for example `de_DE,fr_FR`, whose core language files are installed at first boot. Off by default, because the tarball is about 100 MB and most stacks stay `en_US`. See the notes below the table. |
| `CIVIKITCHEN_DEFAULT_LOCALE` | _(unset)_ | all | The site language. It must be one of `CIVIKITCHEN_LOCALES`. A default without its language files is an error, not a silent fallback to English. Acts at install time only. See the notes below the table. |
| `CIVIKITCHEN_PROFILE` | _(unset)_ | all | One or more comma-separated profiles, applied in order once at first boot: `verein`, `fundraising`, `events`, `mailing`, or one found via `CIVIKITCHEN_PROFILE_PATH`. Needs network access and takes a few minutes. See [Profiles](images.md#profiles-civikitchen_profile). |
| `CIVIKITCHEN_PROFILE_PATH` | _(unset)_ | all | Colon-separated external profile roots. Each holds `<name>/profile.json`. See [Profiles](images.md#profiles-civikitchen_profile). |
| `CK_SEED_SIZE` / `CK_SEED_TODAY` / `CK_SEED_STORE` | `demo` / today / `/var/lib/civikitchen/snapshots` | standalone | Size, generation day and store of [seed snapshots](seed-snapshots.md). `CK_SEED_TODAY` (`Y-m-d`) fakes the day a profile generates for and a restore shifts to. |
| `CIVIKITCHEN_TRUST_EXTERNAL_PROFILES` | `0` | all | Must be `1` before any profile from outside the bundled root may run. It trusts the whole mounted root, including its shell drivers and PHP seeds. |
| `CK_CREDENTIALS_FILE` | web user's `$HOME/api-credentials.txt` | all | Where profile API-user provisioning (`configure-api-users.php`) writes the generated credentials, one `username:password:api_key` line per API user. The default home is `/home/buildkit/` on buildkit flavors and `~www-data/` on the standalone dev image. Profile seeds may write sibling files next to it, such as a site-key export, so copying the whole directory out with `docker cp` picks them up too. |
| `CK_CREDENTIALS_OUTPUT` | `file` | all | How generated passwords and API keys are disclosed. `file` writes only the mode-0600 credentials file. `log` removes any stale file and prints to the container log only. `both` does both. `none` removes any stale file and leaves the new credentials only in the accounts. Logging is opt-in because CI often archives container logs. An unknown value aborts before API users are created. |
| `CIVIKITCHEN_TEST_DB` | `1` | standalone | With `1`, the image sets up the isolated headless test database `<db>_test`, for example `civicrm_test`. On first install it is created, granted and seeded as the database root user. `TEST_DB_DSN` is written on every boot. Set `0` to manage `TEST_DB_DSN` yourself. The boot-stub patch applies either way. See [Headless tests](extension-development.md#headless-tests). |
| `CIVIKITCHEN_EXTRA_PACKAGES` | _(unset)_ | standalone | Comma- or space-separated Debian packages installed on container start, for example `libreoffice-writer,unoconv` for CiviOffice rendering. This keeps heavy or niche dependencies out of the image. Restarts skip packages already present. apt needs root, so the service sets `user: root`, and `docker compose exec` then needs `-u www-data` for cv and the ck tools. |
| `HTTPD_DOMAIN` / `HTTPD_PORT` | `localhost` / `80` | buildkit | Build the derived default of `CIVIKITCHEN_SITE_URL` as `http://<domain>[:<port>]`. Setting `CIVIKITCHEN_SITE_URL` overrides both. |
| `XDEBUG_MODE` (+ `XDEBUG_CLIENT_HOST`, `XDEBUG_CLIENT_PORT`, `XDEBUG_START_WITH_REQUEST`, `XDEBUG_DISCOVER_CLIENT_HOST`, `XDEBUG_IDEKEY`) | off | all | Xdebug is installed but off until `XDEBUG_MODE` is set, for example to `debug,develop`. Defaults: client `host.docker.internal:9003`, start with request on trigger, client host discovery off, IDE key `VSCODE`. See [IDE step debugging](extension-development.md#ide-step-debugging). |
| `CIVICRM_DB_ROOT_PASSWORD` | `root` | all | Database admin password. civibuild uses it to create the site database and user on the first-run build. The standalone image uses it to create, grant and seed the `<db>_test` database (see `CIVIKITCHEN_TEST_DB`). |
| `CIVIKITCHEN_REINSTALL` | `0` | buildkit | Set to `1` for one boot to let a fresh app container rebuild over an existing civikitchen site in the external database. The marker is a sentinel in `civikitchen_state`, see [Buildkit flavors](images.md#buildkit-flavors-dev). Without it, the boot also refuses when it cannot read the sentinel at all, for example on denied root access or a lost connection, instead of assuming there is no site. |
| `CIVICRM_SITE_TYPE` | tag default | buildkit | The civibuild site type. Defaults: `drupal10-demo` on `:drupal10`, `drupal11-demo` on `:drupal11`, `wp-demo` on `:wordpress`, `joomla-demo` on `:joomla`, `backdrop-demo` on `:backdrop`. Any [civibuild template](https://docs.civicrm.org/dev/en/latest/tools/civibuild/) works. `drupal11-demo` is not an upstream template; CiviKitchen vendors it in [`docker/buildkit/site-types/drupal11-demo/`](https://github.com/civico-de/civikitchen/tree/main/docker/buildkit/site-types/drupal11-demo/). |

## Locales

With `CIVIKITCHEN_LOCALES` set, first boot downloads the `civicrm-<version>-l10n.tar.gz` that matches the installed version from download.civicrm.org and unpacks only the requested locales into `[civicrm.l10n]`. An alpha or beta core, such as `:standalone-master` or `:standalone-beta`, takes core's daily `civicrm-l10n-daily.tar.gz` instead. A stalled download is aborted and retried; an unknown locale fails the boot rather than leaving English behind.

Without core language files, core strings stay English. An extension's own `l10n/<locale>/LC_MESSAGES/<file>.mo` still translates (measured on 6.16 and 6.18), so testing an extension's catalogue needs no core language files.

`CIVIKITCHEN_DEFAULT_LOCALE` installs the standalone site in that language. The language files are fetched before `cv core:install --lang=<locale>` runs. The seed data labels, such as financial types, membership statuses, location types and payment instruments, come out translated while their machine names stay English. The installer also applies core's defaults for the locale from `settings/l10n/<locale>/settings.default.json`; for `de_DE` that means EUR, Germany, ISO dates and Europe/Berlin. An existing site keeps its data. The buildkit flavors create their site with civibuild and only set `lcMessages` afterwards, so their seed labels stay English.
